# Project notes

What this project is, how it is put together, and the decisions behind it.

## What it is

DiseaseWise is a public information site about diseases and remedies, plus a
private admin area where an administrator writes and edits that content.

This repository holds **the frontend only**. The backend does not exist yet.
Every piece of content currently lives in the sample data in `src/data` and
changes are lost when the page is reloaded.

```bash
npm run dev        # the site on http://localhost:5173
```

signing in, filling in a form, saving, deleting, renaming.

## The test suite

Milestone 8 asked for a real test framework, and there is one now: Vitest
with Testing Library, in `tests/`.

| File | Tests | What it covers |
|---|---|---|
| `tests/contract.test.ts` | 80 | The service contract: the search rules, the suggestions, one disease, the featured rule, the no-dosage rule, the categories and every admin action |
| `tests/admin.test.tsx` | 19 | The admin pages, the guard, the forms, the notices and the awkward content |
| `tests/public.test.tsx` | 18 | The public pages: home, search, disease, remedy, categories, about and not found |
| `tests/content.test.ts` | 15 | The content rules for the sample data |
| `tests/structure.test.ts` | 47 | The architecture rules and the handover package |

Nothing is faked. The tests open the real routes, through the real router,
with the real services and the real sample data, so a passing test means the
app really behaves that way.

The two old one-off check scripts, `scripts/smoke.ts` and
`scripts/adminCheck.tsx`, were deleted. Their checks are now the first two
test files, so there is one place for each rule rather than two.

The last test file is the unusual one. `tests/structure.test.ts` reads the
source files and this folder, and fails if a page imports the sample data
behind the services area, if the sample data drifts from the agreed
structure, or if a handover document is missing. The handover package
therefore cannot go out of date quietly.

### The two things the tests needed to be told

**jsdom has no browser features.** The app uses `IntersectionObserver` for
the "read while you scroll" behaviour and `matchMedia` for the dark
preference. jsdom has neither, so `tests/setup.ts` gives it stand-ins that
do nothing. The tests are about what a reader sees, not about scrolling.

**The service results are a union.** A service call either succeeds or
fails, and the data only exists on the success branch. `expectOk` in
`tests/helpers.tsx` does the narrowing in one place, so the tests read as
plain sentences.

## The handover package

The package the backend team receives is in `docs/`, with the index in

The sample data is also written out as a file the backend can load:

## The audit

`npm run audit` is the Milestone 7 check. It builds the site, serves it, and
drives it in a real browser through six screen sizes: a phone, a phone turned
sideways, a tablet, a tablet turned sideways, a desktop, and a desktop at
150% zoom.

It looks for four things.

- **Contrast and accessibility.** Every page is run through axe-core. Each
  failure is reported with the two colours and the ratio, so the fix can be
  worked out without running the browser again.
- **Sideways scrolling.** A page that is wider than the window is a broken
  page on a phone. The tables are allowed to scroll inside their own card,
  but not to push the page sideways.
- **The console.** Warnings and errors are collected. The browser is asked to
  ignore favicon requests; nothing else is ignored.
- **The keyboard.** The skip link has to be the first thing the keyboard
  reaches and it has to move focus into the content. The search suggestions
  have to open, move and be opened with the keyboard alone.

Three things were needed to make the audit trustworthy, and each of them is a
lesson worth keeping.

**The page has to have arrived before it is measured.** The pages fetch their
data before they draw, so a fixed wait can catch a page that is still on its
way and measure the wrong thing. The audit waits for the heading each page is
meant to show, which both proves the page has arrived and proves that the
right page is on screen. An earlier version only checked the address, and it
happily passed a page that was showing the wrong content.

**Motion has to be off.** A colour sampled in the middle of a fade is a
colour nobody ever reads. The audit turns transitions and animations off for
the whole run.

**The admin area has to be reached by clicking.** The placeholder session
lives in the page's memory, so any full page load clears it and the guard
sends the browser back to the sign-in page. An earlier version pushed
addresses into the history instead of clicking, which not only produced a
router warning, it also meant the audit was quietly measuring the sign-in
page over and over. The audit now signs in, then clicks through the sidebar
and the buttons the way an administrator would, which also exercises the
slide-out menu on a phone.

What the audit found and what was changed:

| Problem | Fix |
|---|---|
| The admin tables pushed the page sideways on small screens | `min-w-0` on the admin content column, so a wide table scrolls inside its own card |
| Muted text on the soft panels was just under the 4.5:1 ratio | `muted` deepened from `#64748B` to `#5A6474` |
| Amber, red and green text on their soft backgrounds was well under 4.5:1 | `warning` deepened to `#92400E`, `urgent` to `#B91C1C`, `success` to `#166534` |
| The placeholder text in the admin search and form fields was hard to read | `placeholder:text-slate-500` |
| Enter on a highlighted search suggestion searched for the name instead of opening the disease | The suggestion now opens `/disease/:slug` |

The audit now passes on all six screen sizes: no contrast failures, no
sideways scrolling, a clean console, and the keyboard checks all pass.

**It runs in every browser it finds.** The plan asks for the Part 8 checklist
to be run in at least two browsers. The audit looks for Chrome and Edge on
the machine and gives each one the same run, so the comparison is real
rather than assumed. The last run passed in both, with no findings, over 228
page loads.

## The shape of the code

```
src/
  assets/       the logos
  components/
    admin/      the reusable admin pieces
    disease/    the pieces of the disease and remedy pages
    public/     the pieces of the public site
    search/     the search box, the filter and the result card
    shared/     the pieces used by both
  data/         the sample content and the in-memory store
  layouts/      the public frame and the admin frame
  pages/        the pages themselves
  routes/       the route list and the data loaders
  services/     every call to the data, and nothing else
  types/        the shared shapes, marked [LINK]
  utilities/    small helpers
```

Three rules hold the project together.

**Pages never read the data.** Everything goes through `src/services`. When
the backend arrives, only that folder changes.

**The types in `src/types` are the contract.** They are marked `[LINK]`. The
backend must return exactly these shapes. If the two disagree, the backend is
wrong. See `docs/backend-endpoints.md`.

**The validation lives in one place.** `src/services/validation.ts` holds
every rule. The frontend uses it while typing, and the server must repeat it
exactly. See `docs/admin-security.md`.

## Decisions

**TypeScript.** The plan allows JavaScript or TypeScript. TypeScript was
chosen because the types are the contract with the backend, and the contract
is the part most likely to be got wrong.

**A data router.** The app runs on `createBrowserRouter` rather than
`BrowserRouter`. The admin forms need to block navigation when there are
unsaved changes, and that needs the router's blocker.

**Loaders for the admin pages.** The admin pages get their data from route
loaders, not from an effect inside the page. A page therefore never shows a
half-built screen, and a failed load lands on one error page instead of
scattering error states through the code. The public pages still fetch in an
effect, because they need the search box to feel instant.

**One form for add and edit.** The plan asks for one form, so
`DiseaseForm` and `RemedyForm` each handle both. A new record starts empty,
an edit starts filled in.

**Validation while typing.** The forms run the same validation the service
runs, so a problem shows up as soon as the administrator moves on from a
field, rather than after a round trip. The service still validates, because
the browser cannot be trusted.

**A slug preview, but the server decides.** The form shows the address the
disease will get. The server generates the real slug and the server's wins.

**The category slug never changes.** Renaming a category keeps its address,
so links that point at it keep working. The plan does not say this, but
breaking live links is a poor default.

**The delete button stays disabled.** A category that still holds diseases
cannot be deleted, so the confirm dialog says why and the button is
disabled. The server refuses the same delete anyway.

**Amber and red are for safety only.** Amber is for precautions and for
content that needs attention. Red is for urgent signs and for destructive
actions. Nothing else uses them, so a reader learns what they mean.

**"Featured" means an administrator picked it.** The plan left this open in
section 9.3 and offered "a flag or most recently updated". The flag was
chosen, because the home page section is headed "Popular diseases" and a
list ordered by edit date is not a popular list: fixing a typo would move a
condition to the front of the site. The rule lives in
`src/utilities/featured.ts`, and it needs one extra boolean on the disease
record, which is the one addition to the plan's table in section 4.1. The
disease form has a "Show on the home page" toggle, and the list marks the
diseases that are on it. See `docs/backend-endpoints.md`.

**The dosage rule is a list of named rules.** The plan says no dosages and
no prescription instructions. That is checked by five rules rather than one
long expression, so each one can be read and tested on its own. See
`src/services/validation.ts` and `docs/backend-endpoints.md`.

## Design tokens

The tokens live in `src/index.css` and follow Tailwind v4's `@theme`.

| Token | Colour | Used for |
|---|---|---|
| `primary` | `#0F766E` | Links, primary buttons, the brand |
| `primary-dark` | `#115E59` | Hover and pressed states |
| `primary-light` | `#CCFBF1` | Selected states, soft panels |
| `primary-light-alt` | `#99F6E4` | Borders on soft panels |
| `surface` | `#F8FAFC` | The page background |
| `ink` | `#1E293B` | Body text |
| `muted` | `#5A6474` | Secondary text |
| `warning` | `#92400E` | Precautions, needs attention |
| `urgent` | `#B91C1C` | Emergency signs, destructive actions |
| `success` | `#166534` | "A remedy exists" |

Each of these is the readable shade of its colour. The vivid shade of amber,
red or green is fine as a dot or a border but fails the 4.5:1 contrast ratio
as text, so the deep shade is the one that carries the words and the soft
shade (`warning-soft`, `urgent-soft`, `success-soft`) sits behind it.

Headings are Poppins, body text is Inter. Both load from Google Fonts, with
a fallback stack so the page still reads well if the font never arrives.

## Content rules

These are not negotiable and they are checked in code.

- No dosages and no prescription instructions. `containsDosage` in
  `src/services/validation.ts` refuses them, using five named rules. The
  rules catch a number with a dose unit, a dosing frequency, an interval in
  hours, a dose change instruction and the prescription abbreviations. They
  deliberately leave alone durations, percentages and vague schedules,
  because blocking those would push the reviewer towards worse wording.
- Every remedy needs a source and a last reviewed date.
- A review older than a year is flagged, so old content gets rechecked.
- A disease with no remedy carries `remedy: null`, and the public page says
  so plainly rather than showing an empty section.
- The disclaimer appears on the public site, not only on the about page.
